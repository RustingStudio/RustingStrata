# RustingStrata su Tesla V100 (sm_70)

Piano di lavoro del fork `TheBrutalX/RustingStrata`, ramo `v100`.

Obiettivo: far girare RustingStrata su V100 (Volta, compute capability 7.0) con
entrambi i backend, con numerica corretta e prestazioni almeno pari a llama.cpp
sulla stessa scheda.

Stato al 2026-11-06: **Vulkan funziona** (dopo il fix della shared memory),
**CUDA non parte** (i kernel usano istruzioni sm_80+).

---

## 1. Dati della scheda e vincoli

| Voce | V100-SXM2-32GB |
| --- | --- |
| Compute capability | 7.0 (sm_70), 80 SM, 5120 core FP32 |
| Tensor core | 1ª gen, solo FP16, forma `mma.m8n8k4` (125 TFLOPS FP16) |
| FP16 CUDA core | ~31 TFLOPS |
| INT8 | solo `dp4a` (CUDA core), **nessun tensor core int8** |
| Memoria | 32 GB HBM2, ~900 GB/s, 6 MB L2 |
| Shared memory | 96 KB/SM, 48 KB per workgroup in Vulkan (limite raggiungibile) |
| Driver | 580.178.04 = **ultimo branch che supporta Volta** |
| CUDA | toolkit/NVRTC 12.x (CUDA 13 ha rimosso sm_70) |
| Vulkan | 1.4.312, **senza** `VK_KHR_cooperative_matrix` |

Conseguenze:

- CUDA 13 non è utilizzabile: il fork deve compilare con NVRTC 12.x e
  supportare esplicitamente `--gpu-architecture=sm_70`.
- Il backend Vulkan non può usare i tensor core su Volta (l'estensione
  cooperative matrix non esiste su sm_70): resta il path `*_dp`.
- Per le prestazioni massime l'unica strada è il backend CUDA con kernel
  sm_70 (tensor core FP16 `m8n8k4` oppure FMA FP16).
- La licenza RustingStrata 1.0 consente fork e modifiche (anche per servizi
  commerciali) ma richiede licenza e credito all'autore originale e vieta di
  vendere l'engine stesso. Il fork resta sotto la stessa licenza.

## 6. Fase 2 — Backend CUDA sm_70 (2-4 settimane, il lavoro vero)

Tutto in `src/cuda/kernels.cu` e `src/cuda/mod.rs`. Regola: ogni sostituzione
dietro `#if __CUDA_ARCH__`, senza toccare il codice sm_80+, così il fork resta
allineabile a upstream.

### 2.1 Toolchain e selezione arch (0,5 g)
- `src/cuda/mod.rs:183`: `compute_capability()` → `sm_70`; messaggio d'errore
  che parla di CUDA 13 → accettare NVRTC 12.x.
- Verificare che `cudarc` carichi `libnvrtc.so.12` (qui è la 12.9) e che le
  API usate esistano.
- Aggiungere un log chiaro: `cuda device: ... sm_70 (Volta fallback)`.

### 2.2 Warp reduce (0,5 g)
- `topk_warp` (`kernels.cu:1958-1959`) usa `__reduce_max_sync` /
  `__reduce_min_sync` (sm_80).
- Sostituire con riduzione `__shfl_xor_sync` (log2(32) passi) dietro
  `#if __CUDA_ARCH__ < 800`.

### 2.3 `ldmatrix` → load manuali (1-2 g)
- `ldsm4` / `ldsm4t` (`kernels.cu:821-829`): `ldmatrix` è sm_75+.
- Su sm_70 caricare i 4 registri con `ld.shared.b32` usando gli indirizzi per
  lane che il commento già documenta. Il layout dei frammenti resta identico:
  test di parità con il path CUDA sm_80 e con il reference CPU.

### 2.4 `mma.m16n8k16` → Volta (3-7 g, il pezzo critico)
Usato in `gemm_q` (`kernels.cu:915`) e `attn_prefill_t` (`:2139-2140`).
Due stadi, per ridurre il rischio:

- **2.4a fallback FMA FP16** (`#if __CUDA_ARCH__ < 800`): prodotti f16 con
  accumulo f32 sulle CUDA core (~31 TFLOPS). Semplice, corretto, sblocca
  subito il funzionamento.
- **2.4b tensor core Volta**: `mma.sync.aligned.m8n8k4.row.col.f16.f16.f32`.
  Una `m16n8k16` si scompone in 8 `m8n8k4` (2 righe × 1 colonna × 4 passi K);
  cambiano i layout dei frammenti e il codice che li consuma (softmax di
  `attn_prefill_t`, store di `gemm_q`). Prestazioni tensor-core piene, ma è
  qui che si concentra il rischio.

### 2.5 `cp.async` → prefetch sincrono (2-4 g)
- Helper `cp_async16/8/commit/wait` (`kernels.cu:1014-1023`), usati in
  `gemmi_q` (`:1044-1081`), `attn_decode_t` (`:1733-1798`),
  `attn_prefill_t` (`:2094-2146`).
- Su sm_70: double buffering classico `ld.global` → registri → `st.shared`,
  con la stessa distanza di prefetch; valutare `prefetch.global.L2` per i
  tile successivi. La pipeline perde l'asincronia: è il punto che richiede
  più tuning (Fase 3).

### 2.6 Path int8 (1-2 g)
- Volta non ha tensor core int8: `mma.m16n8k16.s8` / `m16n8k32.s8` non
  esistono.
- Scelta consigliata: `Gpu::mmq()` restituisce `false` per sm_70, così il
  prefill usa il path f16 (già presente). In alternativa portare la logica
  `__dp4a` del path Vulkan `gemmi_dp`.
- Da verificare: i pesi Q4_K/Q5_K passano dal path int8 sul 3060; su V100
  cambiare path cambia i bit, quindi la parità va misurata, non pretesa
  identica a upstream.

### 2.7 Numerica e test (continuo)
- `tools/parity.py` contro llama.cpp, `tests/backend.rs`, `STRATA_MODEL`.
- Confronto CPU reference vs CUDA sm_70 vs CUDA sm_80 vs Vulkan.
- Metriche: top-1 agreement, non solo tok/s.

Criterio di uscita fase 2: `strata generate/bench --gpu --backend cuda` gira
su sm_70 senza errori, parità ≥ 98% con llama.cpp come upstream, numeri
registrati. Solo dopo si passa al tuning.

## 7. Fase 3 — Ottimizzazioni specifiche V100 (1-2 settimane)

Solo dopo la fase 2, altrimenti si ottimizza codice che non gira.

- **CUDA**
  - carveout shared 96 KB (`cudaFuncAttributePreferredSharedMemoryCarveout`)
    e tile più grandi ora possibili;
  - tile/grid per 80 SM (occupancy, register pressure: 64K registri/SM);
  - MoE: prefetch degli esperti del layer successivo, politica di residenza
    (con 32 GB tutti gli esperti stanno in VRAM: il CPU worker deve costare
    zero), L2 6 MB per i pesi caldi;
  - decode GEMV: obiettivo ≥ 85-90% dei 900 GB/s;
  - `--kv q8`, MTP/speculative, `--parallel`.
- **Vulkan** (fallback): tuning `gemmi_dp`/`gemm_f_dp`, local size, numero di
  code, sincronizzazioni; niente tensor core, quindi il tetto resta basso.
- **Target indicativi** su Qwen3.6-35B-A3B Q2 (12.3 GB, tutto in VRAM):
  - CUDA: 4K prefill ≥ 2000 tok/s, decode ≥ 130 tok/s;
  - Vulkan: non regredire (1424 / 110).

## 9. Rischi

| Rischio | Impatto | Mitigazione |
| --- | --- | --- |
| `mma` m8n8k4 e layout frammenti | alto (settimane) | 2.4a FMA prima, tensor core dopo |
| `cp.async` senza equivalente | medio (perf) | double buffering + prefetch L2, misurare |
| Divergenza da upstream | medio | modifiche solo dietro `__CUDA_ARCH__`, rebase settimanale |
| NVRTC 12 vs 13 | basso | rilevare versione all'avvio, messaggio chiaro |
| Volta EOL (driver 580) | basso ora | fissare driver/toolkit nei docs |
| Licenza | basso | mantenere LICENSE e credito, niente vendita dell'engine |
